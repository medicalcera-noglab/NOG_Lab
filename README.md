# NOG Lab — noglab.org

Research lab website for the **Nutrition, Oral and Gut Microbiome Lab**
at Khyber Medical University.

Public marketing/science site + self-service admin CMS in a single repo, single deploy.

---

## Tech Stack

- **Next.js 16** (App Router, TypeScript, Turbopack)
- **Payload CMS 3.x** — embedded in the Next.js app, admin at `/admin`
- **PostgreSQL + PostGIS** — via Payload's Drizzle/Postgres adapter
- **Tailwind CSS 4** — utility-first, token-driven
- **next-themes** — dark/light with `data-theme` attribute
- **framer-motion** — scroll-reveal animations (respects `prefers-reduced-motion`)
- **Lucide React** — line icons
- **Fonts**: Plus Jakarta Sans 700 (headings), Inter 400/500 (body)

---

## Prerequisites

- **Node.js 22** (required — Node 24 breaks the Payload CLI; use `nvm use 22`)
- npm ≥ 10
- PostgreSQL ≥ 14 with **PostGIS** extension installed (`CREATE EXTENSION postgis`)

## Local Setup

```bash
# 1. Clone and install
git clone <repo-url> noglab
cd noglab
npm install

# 2. Set up environment
cp .env.example .env.local
# Edit .env.local — fill in DATABASE_URI and PAYLOAD_SECRET

# 3. Create the local database
createdb noglab   # or use psql / pgAdmin

# 4. Start the dev server (Turbopack)
npm run dev
```

The app is now running:

| URL                         | Description             |
| --------------------------- | ----------------------- |
| http://localhost:3000       | Public site             |
| http://localhost:3000/admin | Payload CMS admin panel |

On first run, Payload will run migrations and prompt you to create the first admin user.

## Migrations

This project uses **explicit migration files** — schema is never auto-pushed. Migrations run in
timestamp order: PostGIS extension → full schema → geography column conversion.

### Run migrations (via Payload's built-in runner)

Migrations run automatically on `npm run dev` / `npm run build` when pending. To run manually:

```bash
npm run payload migrate
```

### Create a new migration after changing collections

**Must use Node 22** (the Payload CLI breaks on Node 24):

```bash
nvm use 22
npm run payload migrate:create
```

This generates a timestamped file in `migrations/`. Commit it with your collection changes.

### Migration order

| File                                   | Purpose                                                                |
| -------------------------------------- | ---------------------------------------------------------------------- |
| `20240101000000_enable_postgis.ts`     | Enables `postgis` + `postgis_topology` extensions                      |
| `20260618_201421.ts`                   | Full schema (auto-generated by Payload)                                |
| `20260618_201422_postgis_geography.ts` | Converts `study_sites.location` → `geography(Point,4326)` + GiST index |

> **Why geography(Point,4326)?** Payload's `point` field creates `geometry(Point)`. The third
> migration converts it to `geography` so PostGIS distance functions use metres on a spheroid
> (accurate for Pakistan-scale distances) rather than planar degrees.

### Verify PostGIS column after migration

```sql
SELECT c.column_name, c.udt_name, g.type, g.srid
FROM information_schema.columns c
JOIN geometry_columns g
  ON g.f_table_name = c.table_name
  AND g.f_geometry_column = c.column_name
WHERE c.table_name = 'study_sites' AND c.column_name = 'location';
-- Expected: udt_name=geography, type=Point, srid=4326
```

### Seed demo data

Once migrations are applied, populate the database with realistic Pakistan demo data:

```bash
npm run seed
```

The seed script is idempotent — safe to run multiple times.

## Generating Payload Types

After modifying Payload collections, regenerate types:

```bash
npm run build
# or, without a full build:
npm run payload generate:types
```

`payload-types.ts` at the root is auto-generated — do not edit it manually.
